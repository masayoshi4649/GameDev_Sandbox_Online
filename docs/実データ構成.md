# 実都市データの再取得と配布

この試作は、台場・有明・東雲・豊洲を含む東京湾岸の公開都市データを、変更・撤去可能な初期都市へ取り込む。実建物、道路、道路形状から推定した接続点と信号器はすべて個別の識別子を持つ。実都市を編集して始める方法と、地形だけを残した更地から始める方法を用意している。

公開データは編集不能な背景ではない。未変更の建物は元の屋根・壁面・写真を維持し、形状を変更した建物だけを設計値から再生成する。地形も盛土・掘削・整地・平滑化・水面高変更を保存・同期できる。初期表示の航空写真は無効で、参照表示を選んだ場合だけ読み込む。

## 初回の準備

Windows x64 の PowerShell で、リポジトリのルートから実行する。

```powershell
.\import-world.ps1
```

Node.js 22 以降と Python 3.14 以降が見つかれば使用する。この作業環境で確認した版は Node.js 24.14.0、Python 3.14.3。見つからない場合は、それぞれの公式配布元から同じ版を `build/import-runtime/` に準備する。Node は公式 SHA-256 一覧、Python は公式配布ページの SHA-256 と照合する。OS の PATH を恒久的には変更しない。

取り込み時に必要なライブラリは次のとおり。ゲーム起動や専用サーバー実行に Node・Python は不要。既定は元写真 z18、地表 65 × 65 頂点。写真の同時取得は最大 6 件に制限する。

| 用途 | 依存 |
| --- | --- |
| 3D Tiles の圧縮メッシュ復号 | Google 公式 Draco の `draco3dgltf 1.5.8`。`Tools/ImportPlateau/package-lock.json` で固定。 |
| 地図・水域の範囲抽出 | `pmtiles 3.8.1`、`mapbox-vector-tile 2.2.0`、`shapely 2.2.0`。 |
| 画像読み書き | `Pillow 12.3.0`。 |
| Python の依存先 | `Tools/ImportGround/.venv/` 内。固定指定は同フォルダーの `requirements.txt`。 |

スクリプトは必要な依存だけを準備し、建物、写真・地表、結果検査の順に実行する。GLB 約 382 MiB に加え、高解像写真と地表、元配信のキャッシュ、Python 環境、Godot の取込結果を保存する空き容量が必要。

通常の取り込み後は建物写真を2Kの表示用キャッシュへ事前変換する。出力先は `import-world.ps1` の `$textureCacheDirectory` で、GLBのSHA-256と画像番号を名前に含める。ゲーム実行時は `user://cache/urban-textures/v1-2048/` を参照し、標準のWindows環境では `user://` は `%APPDATA%/Godot/app_userdata/都市づくり/` に対応する。旧アプリ名の場所にあるキャッシュは、新しい保存先へ配置しない限り再利用されない。`-SkipTextureCache` で事前生成を省略、`-TextureCacheSize 4096` などで表示用上限を変更できる。変更したサイズのキャッシュを使うゲーム側にも `--urban-texture-size=4096` のように同じ値を渡す。キャッシュがない場合は実行時に生成するため、初回の読込は長くなる。

すでに取得済みなら、次のコマンドで通信せずに成果物を確認できる。依存の導入やデータの再生成も行わない。

```powershell
.\import-world.ps1 -SkipDownload
```

検査対象は CPU 用 JSON 4 ファイル、明細に記載された建物 GLB 全件の存在・サイズ・SHA-256、個別編集用の地物対応表216件の存在・SHA-256、写真196枚、地表196タイル、建物件数と高さ配列の長さ。対応表は `tile.featurePath` と `tile.featureSha256` を使って照合する。記録は `artifacts/import-world-日時.log`、結果と CPU データの SHA-256 は `artifacts/import-world-result.json` に保存する。

通常の取り込みを再実行すると元配信のキャッシュを再利用し、GLB・JSON は再生成する。初回以外に同じ元データを重複取得する必要はない。写真の 404 応答も保存し、同じ未整備 URL を繰り返し照会しない。配信状況を更新したい場合は該当キャッシュを更新する。

## 対象範囲・座標・詳細度

| 項目 | 設定 |
| --- | --- |
| 対象範囲 | 東経 139.760～139.830 度、北緯 35.610～35.670 度。隣接する中央区・港区・品川区の一部も含む。 |
| 原点 | 東経 139.795 度、北緯 35.640 度、WGS84 楕円体高 0 m。 |
| ゲーム座標 | 1 単位 = 10 m。X が東、Y が上、Z が南。 |
| 変換 | WGS84 地心座標 ECEF から原点の ENU へ変換。建物と地表で共通。 |
| 建物の年度 | PLATEAU 2025 年度の中央区・港区・江東区・品川区。 |
| 2D 地図の時点 | 国土地理院最適化ベクトルタイルの 2026 年 7 月 1 日時点データ。 |
| 写真 | PLATEAU-Ortho 2023。未整備・透明部分を国土地理院の全国最新写真で補完。 |

2026 年 10 月 16 日取得分は **18,318 棟**、LOD2 **9,229 棟**、原典に含まれる LOD1 **9,089 棟**、描画用 GLB **216 個**。正本は `plateau-manifest.json` の `statistics`。LOD2 配信にも LOD1 の建物が併録されるため、棟ごとの原典属性を読み分けている。別の LOD1 配信とも地物 ID を照合し、重複させず不足分だけ補完する。

未変更の建物の屋根・壁面・公開写真テクスチャを維持している。全棟に写真テクスチャがあるわけではなく、内装や分解可能なゲーム用建築部品は含まない。建物全体が対象範囲に交差すれば、その建物全体を取り込む。

全216GLBに、各サーフェスの三角形を建物IDへ結び付ける `.features.json` を生成する。元の三角形はまとめて描画しながら、変更・撤去対象の建物の三角形だけを除去できる。階数・高さ・敷地・屋根を変更した建物は入力した値から生成した形状へ置き換わり、元写真を変更後の架空形状へ無理に貼り直さない。名称・用途だけの変更は原典形状を維持する。対応表の全三角形・建物ID・GLB accessor位置の独立検査は `Tools/ImportPlateau/verify-editable.mjs` で実施できる。

クライアントのGPUメモリー使用量を抑えるため、建物写真の表示用テクスチャの長辺は既定で2,048画素までとする。起動引数 `--urban-texture-size=256..8192` で変更できる。原典のGLB・写真データ・形状・UVを変更する処理ではない。表示用画像は縮小し、透明画像はPNG、それ以外は品質96のJPEGへ変換してキャッシュする。

原典を含めない更地・交通試験街区では、クライアントも原典GLBの読み込みを休止する。原典を有効にした時だけ未読キューから読み、無効化した後は残りを休止する。既に読んだタイルを同じ実行中に再取得する方式にはしない。CPU用の地物・道路・標高データと、現在の街区の描画はこの休止中も使用する。`Tests/SourceLoading.tscn` は実ファイルの読込件数、原典を待たない新設地物の描画、有効化・無効化・再開を検証する。

2026年10月16日のWindows GPU実行で、原典非表示の16地物の試験街区はGLB読込0件、地物描画準備の `BAYFRONT_EDITABLE_READY elapsed_ms` が918msだった。修正前の同ログ114,789msは原典を不要な都市でも待っていた時の値である。これは地物描画の準備区間の一例で、CPUデータ取得、地形生成、プロセス起動からの総時間や一般端末の性能を示す値ではない。

原典から階数を取得できない建物は `Floors=0` の未設定とし、モデルの高さを使う。利用者が階数と階高を設定するとその積で高さを再生成する。延床面積と設計定員は設定した階数に基づくゲーム内の計算であり、原典にない階数や現実の人口を推定して確定値にしていない。

地表写真は **z18 の元写真 3,136 枚**を取得し、各 16 枚を 1,024 × 1,024 画素のアトラスへ結合する。配置用タイルは z16 の **196 枚**を維持し、細かい写真へ更新しても描画タイル数は増やさない。原点付近の配信画素間隔は約 **0.49 m**。高解像の元タイルが双方の配信にない部分は、低解像代替であることを個別の出典情報に明記する。

今回の取得結果は全 3,136 領域が実 z18 で、低解像代替は 0 件。写真アトラス合計約 74.4 MB、地表形状合計約 63.4 MB。画素間隔の計算値は 0.4853 m。

地表高は公式配信カタログの楕円体高 Terrain-RGB を使用する。配信画像の画素間隔は原点付近で約 **3.9 m**、写真参照用の地表は **約 7.8 m 間隔**の 65 × 65 頂点へ標本化する。写真・標高の配信画像の細かさは元撮影・測量の精度保証ではない。参照用ファイルを小さく作る場合は次を指定できる。

```powershell
.\import-world.ps1 -MeshSize 33 -PhotoZoom 16
```

CPU の元の高さ参照は 513 × 513 配列へ保存する。通常ゲームの編集地形はこの配列と陸水境界を土台にし、保存順の連続ブラシを適用する。通常描画は16×16パッチ、各33×33頂点の基本格子に最近のブラシ中心・斜面・外縁の座標を加える。写真参照用の65×65メッシュと通常の編集地形は別の描画経路である。

楕円体高は平均海面からの標高とは異なり、この範囲の地面がゲーム内の Y 約3～5にあるのは座標基準による。初期海面は原典水域の高さの中央値で、この取得分はENU Up約35.73m。元DEMは海底測深を表さないため、ゲームの水域は初期海面より最低3m下、原典の陸地は最低0.4m上になるよう補正する。元ファイルは変更しない。地形操作後の陸水は現在の高さと可変海面から判定する。単位・補正・微細ブラシと描画解像度の限界は [編集地形](編集地形.md) に記載する。

地図・写真・建物・標高の整備時点は異なる。工事・造成・撮影条件による局所的な位置差や基部の残差がある。詳細な取得処理・制約は [PLATEAU 取込](PLATEAU取込.md) と [地表データ](地表データ.md) を参照。

## 描画用と CPU 用の分担

| 配置先 | 内容 | クライアント | 専用サーバー |
| --- | --- | --- | --- |
| `Assets/RealWorld/Plateau/*.glb` | 建物の三角形・法線・UV・写真 | 読む | 配布不要 |
| `Assets/RealWorld/Plateau/*.features.json` | 三角形と建物IDの対応表 | 原典形状の個別編集に使う | 配布不要 |
| `Assets/RealWorld/Ground/*.jpg` | 地表の航空写真 | 参照表示を選んだときだけ読む | 配布不要 |
| `Assets/RealWorld/Ground/terrain-*.json` | 写真参照用の地表三角形・UV | 参照表示時に読む | 配布不要 |
| `Data/RealWorld/ground.json` | 実陸地の外周・穴、実水域、道路中心線、描画参照・出典 | 読む | 読む |
| `Data/RealWorld/buildings.json` | 地物 ID、名称・用途・高さ、建物の水平凸包・境界 | 読む | 読む |
| `Data/RealWorld/elevation.json` | CPU 用の高さ配列 | 読む | 読む |
| `Data/RealWorld/plateau-manifest.json` | 原典・変換条件・件数・ファイル明細・ハッシュ | 読む | 同じデータ版を同梱 |

サーバーは GPU 用の三角形・写真を生成せず、地物の寸法・敷地・道路接続・信号の参照先・地形要求の検証、都市時間、実住民と目的交通、共同編集同期、保存を担当する。新しい設計画面の自由建設は原典を固定障害物として扱わず、編集・撤去した地物の状態を使用する。

CPUの原典建物輪郭は実頂点の水平凸包で、中庭や凹部の境界そのものではない。形状編集時はこの輪郭または入力した頂点を使って再生成する。原典の詳細屋根と写真を保持する未変更の形状とは区別する。

未変更の原典建物をマウスで選択するときは、描画用として読み込んだ同じ三角形を使い、壁・屋根・張り出し・凹部を検査する。編集後は現在の敷地・回転・高さを持つ形状で検査し、外接箱の入口だけで地物全体を棄却しない。これらの三次元選択はクライアントの機能で、専用サーバーへ原典三角形を追加配布する必要はない。

道路幅は原典の幅員区分からの参考値。初期車線数・車線幅・歩道幅・速度・立体交差の高さはゲーム用の推定で、公的な確定属性ではない。接続点は同じ高さ階層の道路端点や交差を1mの許容差でまとめて推定し、信号器も道路形状から候補を配置する。信号の実在位置・現示・周期を取得したものではなく、初期の推定信号は未設定で利用者が制御を設定する。

Linux 専用サーバーの配布では `Assets/RealWorld/` を除外し、`Data/RealWorld/` の4ファイルを含める。ゲーム画面の表示とCPUの共有都市処理は独立し、GPU不要の構成である。Windows上の描画なし計算・通信・保存とLinux向け配布物の生成は検証済みだが、Linux実機・WSL・Docker上の起動は未検証。書き出し手順と検証範囲は [専用サーバー](専用サーバー.md) を参照。

設計の保存・共有は `CityState.Edits` の編集差分を使う。原典を含める設定、原典地物の置換・削除、新設地物、地形ブラシと水面高を記録し、全地物が編集対象になる。都市名は `CityState.CityName`、時計は `SimulationTick` と端数、実住民・目的地・個体の経路は `CityState.Simulation` に保持する。数百MBの原典GLBや写真を編集のたびに送る方式ではない。ホスト・参加者・専用サーバーには同じ基礎データ版を用意する。都市の正本を持つ側がホストまたはサーバーとなり、参加者は正本を保存しない。ホスト切断時は参加も終了する。

編集は期待する版番号を伴うコマンドとしてホストへ要求し、検証後に確定する。実行中は取消・やり直しができる。保存ファイルに履歴の全コピーは含めず、確定した都市定義と進行状態を保存する。時計・交通の進行だけでは編集版を更新せず、設計と別の通知で同期する。

現在の目的交通は、住宅からの段階入居、徒歩・車・鉄道・船による目的地への移動、道路分断・通行方向・信号・先行車待ちを扱う。原典の階数未設定の建物は床面積定員を確定せず、実都市全人口を自動生成しない。個別計算は最大512人で、列車・船の共有ダイヤ・多数旅客、貨物、経済と供給網は未実装。[目的交通と編集操作](目的交通と編集操作.md) に必要な用途・接続と制約を記載する。

画面上のゲーム名は「都市づくり」、都市名は保存ごとの任意指定とする。「東京ベイ」という都市名も指定できる。複数保存は `user://cities/saves/<保存識別子>.json` に分け、都市名をファイル名へ転用しない。`real-bayfront`、`BayfrontSandbox` などの内部名は地図・保存・配布の互換用として維持する。

## 別環境への配布とデータ更新

大容量の表示用GLB・地物対応表・写真・地表ファイルはGit管理から除外している。新しい環境でリポジトリを取得しただけでは描画データは揃わないため、`import-world.ps1` を実行するか、取り込み済みの `Assets/RealWorld/` と対応する `Data/RealWorld/` をまとめて渡す。旧版のGLBだけでは個別変更・撤去ができないため、対応表も同じ明細の組として配布する。

元データのキャッシュは `Tools/ImportPlateau/cache/` と `Tools/ImportGround/cache/`。再現用に同じ原典を保持したい場合はこれらも保管する。キャッシュを削除して取得し直すと、現行の 2D 地図・標高配信などは更新されている可能性がある。日時を含む明細 JSON は、同じ地物でも再生成ごとにファイルハッシュが変わる。

データ版を更新する場合は、次の順に作業する。

1. 取り込みコード内の年度・範囲・原点などを意図した設定へ変更する。建物の年度は `Tools/ImportPlateau/import.mjs` で 2025 年度に固定している。
2. 原典キャッシュの扱いを決めて取り込みを実行し、件数・出典・表示と CPU 判定を確認する。
3. `Scripts/BayfrontMap.cs` の `MapVersion` を手動で増やす。別の範囲・別の原点に切り替える場合は `MapId` の扱いも検討する。
4. 更新した描画データと CPU データを同じ組としてクライアントへ配布し、サーバーには同じ版の CPU データを含めて再書き出しする。

現行の版照合は `MapId` と `MapVersion`。取り込み処理が自動でゲーム側の版を変更したり、異なる基礎地形の既存保存を移植したりはしない。同じ版番号のまま一部の地表ファイルだけを差し替えないこと。

## 出典・利用条件

取得元 URL、加工内容、利用条件の参照先は `ground.json` と `plateau-manifest.json` に保存する。ゲーム内表示と配布時の説明に出典を残す。

| 原典 | 確認した根拠 |
| --- | --- |
| PLATEAU の建物・写真・地形 | [公式サイトポリシー](https://www.mlit.go.jp/plateau/site-policy/) は PDL 1.0 と CC BY 4.0 との互換性、出典・加工表示を説明。個別データの権利表示を優先する。 |
| 国土地理院最適化ベクトルタイル | [公式提供仕様](https://github.com/gsi-cyberjapan/optimal_bvmap) は国土地理院コンテンツ利用規約への準拠と出典表示を指定。基本測量成果とは位置付けていない旨を記載。 |
| 国土地理院全国最新写真 | [公式利用区分](https://maps.gsi.go.jp/help/use.html) の「基本測量成果以外で出典の記載のみで利用可能」に写真を掲載。ほかの地図・測量成果の利用区分と混同しない。 |
| 楕円体高 Terrain-RGB | [公式配信カタログ](https://tile.plateauview.mlit.go.jp/tiles/catalog.json) と [TileJSON](https://tile.plateauview.mlit.go.jp/mapbox/tilejson.json?format=png) は PLATEAU・Mapterhorn・国土地理院を出典として指定。 |

[Mapterhorn の原典一覧](https://download.mapterhorn.com/attribution.json) にある日本の DEM は国土地理院の基盤地図情報で、利用条件に国土地理院長承認（使用）`R 8JHs 131` を記載している。これは配信元の加工に関する表示で、このゲームが独自に承認を取得したという意味ではない。

PLATEAU の地形説明には raster-dem を調整中とする記述が残るが、取得日の公式カタログでは実際に公開されていたエンドポイントを使用した。将来も同じ URL・提供内容が維持されるとは限らないため、更新時は配信カタログと個別条件を確認する。
