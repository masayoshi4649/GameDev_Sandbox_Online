# 描画しない中央サーバー

Linux x86_64 の常設サーバー向けに、都市の正本、建物・道路・交差点・信号の設計変更と撤去、地形・水面の変更、目的交通、共同編集要求の検証、同期と保存を扱う配布構成を用意しています。CPU処理だけのサーバー動作はWindows上で検証済みです。Linux用成果物は生成していますが、Linux実機・WSL・Docker上の起動と運用は未検証です。現在の接続上限はクライアント7人で、画面の描画は各クライアント、都市の保存と計算は中央サーバーが担当します。

実地図は地図ID `real-bayfront`、バージョン `1` です。PLATEAU建物18,318棟、地理院道路11,004区間、陸水境界と地表高を計算用JSONとして同梱します。原典建物と道路も個別の編集・撤去対象で、共有都市には原典を含める設定、原典地物の変更・削除、新設地物、地形ストロークと水面高を保存します。GLB・写真・三角形対応表をサーバーへ持ち込む必要はありません。

原典で不明な建物階数は未設定です。初期の車線・速度・高架高と、道路から生成する交差点・信号器はゲーム用の推定で、実際の交通規制を表す確定値ではありません。信号現示は設定した秒数と都市時間から計算し、交通側の進入判定にも使用します。

用途と階数を設定した住宅へ段階的に入居し、徒歩・車・鉄道・船で職場などの目的地へ移動します。住民、目的地、移動途中の経路をCPUで保持し、切断した接続、通行方向、赤信号、先行車待ちを反映します。個別計算は最大512人、住民と乗り物を合わせて最大1,024件です。列車・船は目的旅客から生成する最小実装で、共有ダイヤ、多数旅客の相乗り、貨物、経済、電気・水道は未実装です。[目的交通と編集操作](目的交通と編集操作.md) に現在の制約を記載しています。

編集コマンドはホスト上で順に検証し、古い版に基づく競合、未知の原典ID、不正な寸法・形状・参照先・地形値を拒否します。取消・やり直しもホストで確定して参加者へ同期します。原典GLBや写真を編集のたびに配信する方式ではなく、参加者には同じ地図版の描画データをあらかじめ用意します。現在は自由建設を既定にし、設計寸法・階数からの定員・面積・費用はゲーム用の試算として扱います。

都市時計と交通の進行は編集版を増やしません。時計の通知と圧縮した交通の稼働通知を使い、都市の全設計を毎秒配信する処理を避けています。都市名も保存・同期する状態で、固定のゲーム名は「都市づくり」です。地図ID `real-bayfront`、`BayfrontSandbox.dll`、配布ファイル名、環境変数の `BAYFRONT_` は互換用の内部名として維持します。

専用モードは `--server` またはエクスポート時の `dedicated_server` 機能で選択します。通常の都市画面、カメラ、建物メッシュ、フォントは生成しません。Godot 4 は `--headless` により表示と音声を実体のないドライバーへ切り替えられるため、専用の GPU や画面サーバーを必要としません。[Godot 公式の専用サーバー手順](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_dedicated_servers.html)に基づく構成です。

本書の構成対象は Debian 12 相当の glibc を使う x86_64 環境です。ARM、Alpine Linux の musl 環境へそのまま配布する構成ではありません。

## Windows から Linux 用成果物を作成

このプロジェクトでは Godot .NET 4.7.2 と .NET 8 SDK を使います。通常の Godot 版には C# の実行機能がないため、エディターとエクスポートテンプレートをともに .NET 版で揃えます。ビルドする Windows に Linux 版エディターを追加する必要はありません。[Godot の C# 要件](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)を参照してください。

1. Godot のエクスポートテンプレート管理画面から、使用中のエディターと一致する .NET 版テンプレートを導入します。[4.7.2 の公式配布ページ](https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable)でバージョンを確認できます。
2. 同梱の `BayfrontSandbox.sln` と `.csproj` が揃っていることを確認し、プロジェクトルートで `./export-server.ps1` を実行します。SDK は `%LOCALAPPDATA%\Microsoft\dotnet\dotnet.exe` から検出し、そこにない場合は `PATH` を調べます。Godot の場所が異なる場合は `-GodotPath`、出力先を変える場合は `-OutputDirectory` を指定できます。Godot の .NET エクスポーターはソリューションを必要とするため、`.csproj` 単独の通常ビルド成功だけでは配布物の生成を確認できません。
3. `build/server/` の出力全体を Linux へコピーします。

この作業環境には、公式の `.tpz` アーカイブから Linux x86_64 の release と debug テンプレート、および `version.txt` を部分取得し、ZIP 内のサイズと CRC を確認して導入しています。導入先は `%APPDATA%\Godot\export_templates\4.7.2.stable.mono\` です。release の書き出し前にも Godot が両テンプレートの存在を検証するため、Linux の両方を導入しています。その他の OS 用テンプレートは、この部分導入には含まれません。

同梱プリセット名は **Linux 専用サーバー**、出力先は `build/server/BayfrontServer.x86_64` です。Godot 4.7.2 の正式なプラットフォーム名は `Linux` です。以前の `Linux/X11` という名前は使用していません。[Godot 4.7.2 のプラットフォーム登録処理](https://github.com/godotengine/godot/blob/4.7.2-stable/platform/linuxbsd/export/export.cpp)で確認できます。

スクリプトを使わず直接エクスポートする場合の PowerShell 例です。先にテンプレートを導入し、SDK を `PATH` へ追加してください。

```powershell
$env:PATH = "$env:LOCALAPPDATA\Microsoft\dotnet;$env:PATH"
New-Item -ItemType Directory -Force build/server | Out-Null
& 'S:\Godot_v4.7.2-stable_mono_win64\Godot_v4.7.2-stable_mono_win64_console.exe' `
  --headless --path . --export-release 'Linux 専用サーバー' `
  'build/server/BayfrontServer.x86_64'
```

エクスポートされたフォルダーは、概ね次の構成になります。生成された追加ファイルも含めて配布してください。

```text
build/server/
├── BayfrontServer.x86_64
├── BayfrontServer.pck
├── run-server.sh
├── OFL.txt
├── export.log
└── data_BayfrontSandbox_linuxbsd_x86_64/
    ├── BayfrontSandbox.dll
    ├── GodotSharp.dll
    ├── *.deps.json / *.runtimeconfig.json
    ├── libcoreclr.so などの Linux 用ランタイム
    └── その他の生成された依存ファイル
```

Godot .NET のエクスポーターは Linux 向けの自己完結型 .NET ビルドを生成し、`data_...` フォルダーへ配置します。`.pck` やアプリの `.dll` だけでは不足します。Windows エディターに隣接する `GodotSharp/` フォルダーをコピーする方法ではなく、エクスポーターが生成した Linux 用出力を丸ごと使ってください。[4.7.2 の .NET ビルド処理](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/mono/editor/GodotTools/GodotTools/Build/BuildSystem.cs)、[配布ファイルの生成処理](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/mono/editor/GodotTools/GodotTools/Export/ExportPlugin.cs)を参照しています。

PCKには計算用の `Data/RealWorld/ground.json`、`elevation.json`、`buildings.json`、`plateau-manifest.json` の4点を含めます。`Data/bayfront.json` は簡略地図への互換用です。`Assets/RealWorld/` のGLB、個別建物の三角形対応表、航空写真、地表描画メッシュと、`Assets/Fonts/` のフォント本体は専用サーバーへ含めません。クライアントのGPU用アセットをLinuxサーバーへ別途コピーする必要はありません。出典と利用条件を記したテキストは配布フォルダーへ同梱します。

このプロジェクトは実行開始時に専用経路へ分岐し、画像や建物メッシュを開かず、カメラや描画ノードを生成しません。専用サーバーの書き出し設定だけに依存せず、実行経路と配布内容の両方で描画処理を省いています。

編集地形はクライアントと同じCPU実装の `UrbanTerrain` へ復元し、共有状態の更新に合わせてブラシと水面高を反映します。陸水判定に編集前の固定地図だけを使い続ける構成ではありません。CPUの高さ関数と、クライアント専用の地表メッシュ・参照写真は分離しています。

## Linux で直接起動

以下は Linux 側で実行する例です。導入とサービス登録のコマンドは管理権限が必要な環境に合わせて実行してください。

```sh
# 管理者が自己完結型 .NET に必要なネイティブライブラリを導入します。
apt-get update
apt-get install -y --no-install-recommends \
  ca-certificates libc6 libgcc-s1 libgssapi-krb5-2 libicu72 \
  libssl3 libstdc++6 tzdata zlib1g
```

この一覧は [Microsoft の Debian 12 向け .NET 依存関係](https://learn.microsoft.com/en-us/dotnet/core/install/linux-debian#dependencies)に基づきます。SDK や別の .NET ランタイム本体は、自己完結型の正しい成果物が揃っていればサーバーへの追加導入は不要です。実行ファイルの依存関係は対象ホストで `ldd ./BayfrontServer.x86_64` と `ldd ./data_BayfrontSandbox_linuxbsd_x86_64/libcoreclr.so` を使って確認してください。

出力全体を `/opt/bayfront/` へ配置し、`server/run-server.sh` も同じフォルダーへコピーします。保存先をサーバーの実行ユーザーが書き込めるよう準備します。

```sh
chmod 0755 /opt/bayfront/BayfrontServer.x86_64 /opt/bayfront/run-server.sh
/opt/bayfront/BayfrontServer.x86_64 --headless -- --server \
  --port=24567 \
  --save-path=/var/lib/bayfront/real-bayfront.json \
  --autosave-seconds=30
```

Godot自身の引数 `--headless` と、アプリの引数 `--server` の間には `--` が必要です。初回は実都市由来の全地物を編集可能な初期都市とし、編集差分のない状態を作成します。保存があれば原典の変更・削除、自由設計した地物、造成と水面高を復元します。破損した保存や異なる地図ID・版では起動に失敗し、元ファイルを上書きしません。従来の簡略地図の保存を実地図へ自動変換する処理はありません。標準出力の `BAYFRONT_SERVER_READY` が起動の目印です。

クライアントの複数保存は `user://cities/saves/<保存識別子>.json` に分かれます。中央サーバーは指定した `--save-path` の1都市を正本として使うため、起動する都市の保存ファイルをこのパスへ配置します。都市名・実住民・目的地・経路・時計も再開対象です。複数の都市を同時に運営する場合はプロセス、UDPポート、保存先を分けます。参加者は共有都市を保存・改名・別都市に置換できません。

起動スクリプトでも同じ設定を使えます。変更する場合は環境変数で渡します。

```sh
BAYFRONT_PORT=24567 \
BAYFRONT_SAVE_PATH=/var/lib/bayfront/real-bayfront.json \
BAYFRONT_AUTOSAVE_SECONDS=30 \
  /opt/bayfront/run-server.sh
```

## 常駐と通信

`server/bayfront.service.example` は systemd の設定例です。事前に `bayfront` ユーザーとグループを作成し、出力全体と起動スクリプトを `/opt/bayfront/` に配置してください。保存ディレクトリは systemd の `StateDirectory=bayfront` により管理されます。

```sh
groupadd --system bayfront
useradd --system --gid bayfront --no-create-home \
  --home-dir /var/lib/bayfront --shell /usr/sbin/nologin bayfront
install -m 0644 server/bayfront.service.example /etc/systemd/system/bayfront.service
systemctl daemon-reload
systemctl enable --now bayfront
journalctl -u bayfront -f
```

ENet の接続には **UDP 24567** を使用します。サーバーのファイアウォール、クラウド側のアクセス設定、NAT がある場合のポート転送で、この UDP ポートを許可してください。TCP ポートを開くだけでは接続できません。既存の VPN を使う場合は、そのサーバー側 VPN アドレスをクライアントへ入力できます。

参加者は同じ地図ID・版の実データを持つクライアントを起動し、共同編集欄にサーバーのアドレスと同じポートを入力します。中央サーバーの都市状態を受け取り、建物・道路・交差点・信号の変更や撤去、造成を要求します。参加者から共有都市の保存・読込・再ホストはできません。切断時は共有状態を破棄し、参加前の自分の都市へ戻ります。ホスト移譲はありません。正本と定期保存はサーバーに残るため、参加者全員が離脱してもサーバーは継続します。アカウント認証と利用者ごとの編集権限は未実装です。

## Docker の例

`server/Dockerfile` は Debian bookworm-slim と必要なネイティブライブラリだけを使います。GPU デバイス、X11、Wayland、VNC、ビルド用 SDK は追加しません。事前に Linux 用成果物を生成し、リポジトリルートから BuildKit 対応の Docker で次を実行します。

```sh
docker build --platform linux/amd64 \
  --build-context artifact=./build/server \
  -f server/Dockerfile -t bayfront-server:local ./server
docker volume create bayfront-city
docker run -d --name bayfront-server \
  --restart unless-stopped \
  --stop-timeout 45 \
  -p 24567:24567/udp \
  -v bayfront-city:/var/lib/bayfront \
  bayfront-server:local
docker logs -f bayfront-server
```

名前付きコンテキスト `artifact` はエクスポート済みフォルダーを渡すためのものです。通常コンテキストを `server/` に限定することで、その `.dockerignore` が適用され、ソースや開発キャッシュをイメージへ持ち込みません。[Docker の名前付きコンテキスト](https://docs.docker.com/build/concepts/context/#named-contexts)を使用しています。

コンテナーは UID/GID `10001:10001` で実行します。名前付きボリュームの代わりに既存のホストフォルダーをマウントする場合、その UID/GID に保存先の書き込み権限を与えてください。自動保存先はイメージ内のアプリ配置とは別の `/var/lib/bayfront` なので、コンテナーを作り直しても同じボリュームから再開できます。

## 停止・バックアップ・復元

通常停止には `systemctl stop bayfront`、`docker stop --time 45 bayfront-server`、またはプロセスへの `SIGTERM` を使います。起動スクリプトは `exec` によりシグナルをサーバーへ直接届けます。サーバーは都市を最終保存してから終了します。強制終了やホストの障害では最後の保存後の変更が失われるため、自動保存間隔を運用に合わせて設定してください。

直接配置または systemd の場合のバックアップ例です。

```sh
systemctl stop bayfront
install -m 0640 /var/lib/bayfront/real-bayfront.json /安全なバックアップ先/city.json
systemctl start bayfront
```

Docker の場合はコンテナーを通常停止したうえで `docker cp bayfront-server:/var/lib/bayfront/real-bayfront.json ./city-backup.json` で取得できます。復元時もサーバーを停止し、元ファイルを別の場所へ退避してからバックアップを `real-bayfront.json` に配置します。所有者と書き込み権限を実行ユーザーへ戻し、同じプロジェクト版で起動してください。稼働中の保存ファイルを書き換えないでください。

## 検証範囲

Linux 向けの release エクスポートを実施し、Linux x86_64 の実行ファイル、実地図の計算用 JSON を含む PCK、`linux-x64` 用の .NET ランタイムとアプリの生成を確認しています。PCK の内訳を調べ、4 点の計算用 JSON が含まれることと、GLB・航空写真・フォント本体が含まれないことを確認しています。配布用 ZIP はリポジトリ内の `artifacts/BayfrontServer-linux-x64.zip`、展開前の出力は `build/server/` です。ZIP を展開すると `server/` フォルダーがあり、その内容を一式配置します。Linux 側で実行ファイルと起動スクリプトへ実行権限を付与してください。

WindowsのGodot .NET 4.7.2で、描画ノード数0の専用サーバー起動、原典建物の編集・撤去、道路・交差点・信号と地形の同期、参加者の保存禁止、切断時の都市復帰、保存と再起動復元、異なる地図と壊れた保存の拒否を自動試験します。住民と四交通手段の計算、実ENetでの個体・経路・都市名同期、時計と交通を編集版から分離することも検証します。旧画面の `InteractionTest`、新設計画面の `UrbanInteractionTest`、CPU地形の `EditableTerrainTests` を含む実行入口は `test.ps1` です。高密度の原典形状は共有都市のスナップショットへ複製しません。

配布ZIPはソース変更と同時に更新されるものではありません。使用するコード版で `export-server.ps1` を再実行し、生成されたフォルダー一式を配備します。Linux向けファイルの生成成功と、Linux上での実行成功は別の検証です。

2026 年 10 月 16 日時点の作業環境は Windows です。公式配布の Linux テンプレートを導入し、Linux 向け ELF 実行ファイル、PCK、`BayfrontSandbox.dll`、`GodotSharp.dll`、`libcoreclr.so` を含む自己完結型 .NET 配布物の生成と同梱を確認しています。Linux 実機、WSL、Docker がこの環境にないため、Linux でのプロセス起動、ネイティブ依存関係、SIGTERM の動作、systemd と Docker の実運用は未確認です。これらは配備先で確認してください。初回はログの起動完了、別クライアントからの接続、保存と再起動での復元、通常停止時の最終保存を確認します。
